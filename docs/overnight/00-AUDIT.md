## 2. Release pipeline and what can ship tonight

- `deploy.sh` runs on the server in `/opt/k9training`: it fast-forwards `main`, builds, recreates `app`, reloads Caddy. A schema change needs `--db-push`, which **auto-approves destructive SQL** (Drizzle `--force`). The demo is public and its data is the owner's showcase.
- The server checkout is on `main`; deploying another branch means changing that checkout. Nothing here does that.
- So: UI-only work could be merged and deployed after review, but **nothing from this branch is deployed tonight**. The owner has not seen the new navigation, pages or homepage, and the later phases add tables. Rollback for every phase is "do not merge the branch"; the live site stays on `1b7a29d`.
- Local checks use a disposable Postgres 15 cluster made with Homebrew's `initdb` in a temp directory, because Docker (Colima) is not running. It holds no real data and is deleted afterwards.

## 3. Constraints that shape the work

- **Showcase mode.** There is no SMS provider and no payment gateway: the sign-in code is the public `12345`, payments go through a demo gateway, and auth refuses to start outside showcase mode. Any password-reset-by-code flow is therefore exactly as open as today's sign-in until a real SMS provider exists. This is recorded as a blocker, not hidden.
- **Repository rules** (`CLAUDE.md`, `docs/`): flat route slices, oRPC contract-first backend, `docs/legacy-pages.md` verdicts (the public header and footer are **Redesign**: a brief first), no new palette, no new libraries without need.
- **Facts not available** (never invented): prices of sport and working courses, the working-breed list, the 2–3 month exception's exact bounds and three course ids, the assessment questionnaire, consent and legal text, partner commission rules, a second phone, a WhatsApp number, authentic mascot art, the slogan decision.

## 5. Hero state rule (Phase C)

1. A new browser session advances the stored hero state by one.
2. Arriving on Home by a link or button (push or replace) advances it by one.
3. Back, forward and reload keep the current one. Waiting on the page never changes it.
4. The server reads the state from a cookie so the right photo is the one painted first; the client writes it on arrival.

## 6. Risks

- Header and footer change under the **Redesign** verdict: the brief is in `01-IMPLEMENTATION-LOG.md`, written before the code.
- Passwords on a demo with a public code add convenience, not security (see section 3).
- Every schema change is additive. None is applied to the live database by this branch.
- A tidy code state matters more than a long feature list: anything not finished is hidden, not faked.
